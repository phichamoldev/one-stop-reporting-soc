# Risk Register & Mitigation Strategy

> **สถานะ: PLANNING ONLY — ทะเบียนความเสี่ยงและมาตรการรับมือเชิงป้องกันสำหรับระบบ Incident Grouping**

---

## 1. เกณฑ์การประเมินความเสี่ยง (Risk Matrix)

- **โอกาสเกิด (Likelihood):** 1 (น้อยมาก) ถึง 5 (เกิดบ่อยมาก)
- **ผลกระทบ (Impact):** 1 (น้อยมาก) ถึง 5 (วิกฤตร้ายแรง)
- **ระดับความเสี่ยง (Risk Score = L × I):**
  - **15 – 25: วิกฤต (Critical / High)** — ต้องมีมาตรการเชิงรุกและแผนฉุกเฉินชัดเจน
  - **8 – 14: ปานกลาง (Medium)** — ต้องมีการเฝ้าระวังและป้องกันในระดับ Code/Architecture
  - **1 – 7: ต่ำ (Low)** — รับความเสี่ยงได้ จัดการตามระเบียบปฏิบัติปกติ

---

## 2. ทะเบียนความเสี่ยงแบบละเอียด (Risk Register Table)

| ID | ประเภทความเสี่ยง | คำอธิบายความเสี่ยง | L | I | Score | มาตรการป้องกันเชิงรุก (Mitigation) | แผนรับมือฉุกเฉิน (Contingency) |
|:--:|------------------|-------------------|:-:|:-:|:-----:|-----------------------------------|--------------------------------|
| **RSK-01** | **Operational** | **การจัดกลุ่มผิดพลาด (False Grouping)**<br>เจ้าหน้าที่กดยอมรับการรวมกลุ่มของคำร้องที่คนละเรื่องกัน | 3 | 3 | **9 (Med)** | • ออกแบบ UI ให้เห็นข้อมูลเปรียบเทียบชัดเจน<br>• ห้ามระบบ Auto-link อัตโนมัติเด็ดขาด (Human-in-the-loop เสมอ) | • มีฟังก์ชัน Soft Unlink ปลดออกได้ทันที<br>• บังคับกรอกเหตุผลที่ปลดออกเพื่อเก็บเป็น Audit Trail |
| **RSK-02** | **Operational** | **ทำ Bulk Action ผิดพลาดครั้งใหญ่**<br>เช่น เผลอเปลี่ยนสถานะ 80 คำร้องเป็น "ยกเลิก" หรือพิมพ์ตอบกลับผิด | 2 | 4 | **8 (Med)** | • มี Confirmation Modal สรุปจำนวนเคสและสถานะใหม่ก่อนกดยืนยัน<br>• จำกัด Bulk Action สูงสุดไม่เกิน 100 รายการต่อครั้ง | • ระบบมี `bulk_action_id` กำกับทุกเคส ทำให้สามารถเขียนสคริปต์ Revert คืนค่าสถานะเดิม (`old_status`) ได้อย่างแม่นยำ |
| **RSK-03** | **Technical** | **LINE Quota เต็ม หรือโดน Rate Limit**<br>เกิดเหตุใหญ่มีผู้แจ้งพร้อมกันนับร้อยราย ระบบพยายามส่งข้อความออกไปจำนวนมหาศาล | 3 | 4 | **12 (Med)** | • ออกแบบคิว `notification_queue`<br>• ใช้กลยุทธ์ Debounce 5 นาทีเพื่อรวบยอดส่งเพียง 1 สรุปข้อความสำหรับกลุ่มเจ้าหน้าที่ | • เปิดใช้ Feature Flag Kill-switch ปิดการส่ง LINE ชั่วคราว<br>• มี Exponential Backoff Retry ใน Worker |
| **RSK-04** | **Performance** | **Query Similarity ทำ Database ช้า**<br>การคำนวณ Trigram Similarity กับข้อความสถานที่ใช้ CPU สูง | 2 | 3 | **6 (Low)** | • ใช้ Hard Filter: กรองเฉพาะหมวดหมู่เดียวกัน (`category_id`) และสถานะที่ยังเปิดอยู่ (`open/in_progress`) ก่อนคำนวณ Trigram<br>• สร้าง GiST/GIN Index บนคอลัมน์ location | • เพิ่ม Limit ผลลัพธ์เหลือไม่เกิน 5 รายการ<br>• ปรับลดความถี่ของการคำนวณ Similarity ให้เป็น Asynchronous Task |
| **RSK-05** | **Security / PDPA** | **ข้อมูลส่วนบุคคลรั่วไหลข้ามผู้แจ้ง**<br>ส่ง Bulk Reply แล้วชื่อหรือเบอร์ของผู้แจ้งท่านหนึ่งหลุดไปแสดงให้ผู้แจ้งอีกท่านเห็น | 1 | 5 | **5 (Low)** | • ระบบส่งข้อความแบบแยกเดี่ยว 100% (Individual Push)<br>• ตรวจสอบ Payload ก่อนส่งว่าไม่มีการเอาชื่อผู้แจ้งคนอื่นมาประกอบในเทมเพลต | • ตรวจสอบข้อความใน Notification Queue<br>• ดึงคิวออกจากระบบทันทีก่อนที่ Worker จะยิงออกไป |
| **RSK-06** | **Data Integrity** | **Deadlock ระหว่างทำ Bulk Update**<br>เจ้าหน้าที่ 2 คนกด Bulk Action พร้อมกันกับคำร้องชุดเดียวกัน | 2 | 3 | **6 (Low)** | • ใช้ Stored Procedure `bulk_update_reports` พร้อมคำสั่ง `FOR UPDATE SKIP LOCKED` หรือการเรียงลำดับ ID เสมอ<br>• รองรับ Partial Success ไม่ Rollback ทั้งก้อน | • ระบบแจ้งเตือนให้เจ้าหน้าที่ทราบว่ารายการใดติด Lock และให้กดลองใหม่อีกครั้ง |
| **RSK-07** | **Adoption** | **เจ้าหน้าที่ต่อต้านหรือไม่คุ้นชิน UI ใหม่**<br>รู้สึกว่าระบบซับซ้อนขึ้น และไม่ยอมใช้ฟีเจอร์ Incident | 3 | 3 | **9 (Med)** | • ออกแบบระบบแบบ Additive: หน้ารายงานแบบเดิมยังคงใช้งานได้ตามปกติ ไม่บังคับว่าจะต้องสร้าง Incident ทุกครั้ง<br>• ออกแบบ UI ให้คลีน ปุ่มลอยปรากฏเฉพาะเมื่อเลือก Checkbox | • จัดอบรม Staff ก่อนเปิดใช้งานจริง<br>• จัดทำคู่มือและวิดีโอแนะนำการใช้งานสั้น ๆ |

## 3. แผนผังการควบคุมและการรายงานความเสี่ยง (Incident Playbook)

```
[ตรวจพบข้อผิดพลาดบน Production]
              │
              ├───> [ด้านข้อความ LINE รั่วไหล/สแปม] ───> ปรับ FEATURE_NOTIFICATION_DEBOUNCE = false
              │
              ├───> [ด้าน Bulk Update ผิดพลาด] ───────> ใช้ Function Revert ผ่าน bulk_action_id
              │
              └───> [ด้านระบบช้า/DB Load สูง] ─────────> ปรับ FEATURE_SIMILARITY_SUGGESTIONS = false
```

## 4. ผู้รับผิดชอบความเสี่ยง (Risk Ownership Matrix)

- **System Architect / Lead Backend:** รับผิดชอบความเสี่ยงเชิงเทคนิค (RSK-03, RSK-04, RSK-06)
- **Product Owner / Lead Backoffice:** รับผิดชอบความเสี่ยงด้านการปฏิบัติงานและการยอมรับของผู้ใช้ (RSK-01, RSK-02, RSK-07)
- **Data Protection Officer (DPO) / Security Lead:** รับผิดชอบความปลอดภัยของข้อมูลและสิทธิ์การเข้าถึง (RSK-05)
