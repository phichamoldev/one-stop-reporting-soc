## 4. ผลการทดสอบ TEST TRACK A — Incident Grouping & Bulk Actions

### 4.1 การทดสอบ Text Similarity ด้วย `pg_trgm`

PostgreSQL `pg_trgm` วิเคราะห์ความคล้ายของข้อความด้วยชุดอักขระ 3 ตัวอักษร (Trigrams):

| คู่ข้อความทดสอบ (Text A vs Text B) | Raw Trigram Sim | Normalized Sim | Decision | ผลการประเมิน |
|-------------------------------------|:---------------:|:--------------:|:--------:|:------------:|
| `"แอร์ห้องประชุมไม่เย็น"` vs `"แอร์ห้องประชุมไม่เย็น"` | **1.0000** | **1.0000** | SIMILAR | ✅ ตรงกันเป๊ะ 100% |
| `"แอร์ห้องประชุมไม่เย็น"` vs `"แอร์ไม่เย็น"` | **0.4167** | **0.4167** | SIMILAR | ✅ ตรวจจับคำย่อยได้ดี |
| `"แอร์ห้องประชุมไม่เย็น"` vs `"ห้องประชุมแอร์ไม่ทำงาน"` | **0.3235** | **0.3235** | DISTINCT | ⚠️ สลับตำแหน่งคำทำให้ Trigram ต่ำ |
| `"แอร์ห้องประชุมไม่เย็น"` vs `"เครื่องปรับอากาศห้องประชุมเสีย"` | **0.1860** | **0.1860** | DISTINCT | ❌ **จุดบกพร่อง Trigram (แอร์ vs เครื่องปรับอากาศ)** |
| `"แอร์ห้องประชุมไม่เย็น"` vs `"ไฟห้องประชุมดับ"` | **0.2667** | **0.2667** | DISTINCT | ✅ แยกปัญหาคนละเรื่องได้ถูกต้อง |
| `"แอร์ห้องประชุมไม่เย็น"` vs `"โปรเจคเตอร์เสีย"` | **0.0270** | **0.0270** | DISTINCT | ✅ ปฏิเสธปัญหาคนละเรื่องได้เด็ดขาด |
| `"แอร์ห้องประชุมไม่เย็น"` vs `"ประตูห้องประชุมล็อกไม่ได้"` | **0.2368** | **0.2368** | DISTINCT | ✅ ปฏิเสธปัญหาคนละเรื่องได้ถูกต้อง |

> **ข้อค้นพบสำคัญ (Key Finding):**  
> `pg_trgm` คำนวณตามตัวอักษรเท่านั้น จึง **ไม่เข้าใจคำพ้องความหมาย (Synonyms)** เช่น คำว่า *"แอร์"* กับ *"เครื่องปรับอากาศ"* ซึ่งมีความหมายเดียวกันแต่ Trigram ร่วมกันเท่ากับ 0 ทำให้ได้คะแนนเพียง 0.1860  
> **แนวทางแก้ไข:** ต้องทำ Synonym Replacement ก่อนส่งเข้า Trigram หรือใช้ AI Semantic Embedding ใน Phase 2

### 5.2 การทดสอบ Notification Queue & Exponential Backoff Retry

จำลองคิวแจ้งเตือนผ่านสถานะ: `pending` $\rightarrow$ `processing` $\rightarrow$ `failed` $\rightarrow$ `retry` $\rightarrow$ `sent`:

```text
[Queue Item: queue-mock-001]
  Attempt 1: ยิง LINE API -> จำลอง Gateway Timeout (HTTP 504)
             -> Status: failed | Error: 'HTTP 504' | Next Retry: +30 วินาที
  Attempt 2: รันรอบสอง -> จำลองติด Rate Limit (HTTP 429 Too Many Requests)
             -> Status: failed | Error: 'HTTP 429' | Next Retry: +120 วินาที
  Attempt 3: รันรอบสาม -> LINE ตอบกลับ 200 OK สำเร็จ
             -> Status: sent   | Total Attempts: 3 | Last Error: null
```
✅ **ผลการประเมิน:** ระบบสามารถกู้คืนความล้มเหลวชั่วคราว (Transient Failure) ได้อย่างสมบูรณ์

## 7. ปัญหาที่ตรวจพบและสาเหตุที่แท้จริง (Problems & Root Causes)

### ปัญหาที่ 1: Trigram ไม่เข้าใจคำพ้องความหมายภาษาไทย (Synonym Blindness)
- **อาการ:** คำร้อง *"แอร์ห้องประชุมไม่เย็น"* กับ *"เครื่องปรับอากาศห้องประชุมเสีย"* ได้ Trigram similarity เพียง 0.1860 ทั้งที่เป็นเรื่องเดียวกัน
- **Root Cause:** Trigram มองข้อความแบบ Character N-gram เมื่อคำสะกดต่างกันสิ้นเชิง แม้ความหมายเหมือนกัน ค่าความคล้ายจึงตกต่ำอย่างมาก

### ปัญหาที่ 2: คะแนนฐาน (Base Score Inflation) ทำให้เกิด False Positive
- **อาการ:** คำร้องที่อยู่คนละอาคาร (`MOCK-F01`) หรือคนละห้อง (`MOCK-F06`) ได้คะแนนรวมทะลุ 80 คะแนน กลายเป็น High Confidence Suggestion
- **Root Cause:** คะแนนจาก Category (40) + Subcategory (15) + Time (10) + Status (10) รวมกันได้ถึง 75 คะแนน ทำให้หากสถานที่ตรงกันเพียงเล็กน้อย คะแนนจะพุ่งเกินเกณฑ์ทันที

## 8. แนวทางแก้ไขและปรับปรุง (Recommended Solutions)

1. **เพิ่ม Gate สำหรับคะแนนสถานที่ (Location Gating):**
   - กำหนดเงื่อนไข: หากค่า `Location Similarity < 0.40` **ห้ามจัดเป็น High Confidence โดยเด็ดขาด** ต่อให้คะแนนรวมจะถึงเกณฑ์ก็ตาม
2. **สร้างพจนานุกรมคำพ้องภาษาไทย (Thai Synonym Dictionary):**
   - แปลงคำศัพท์เฉพาะทางอาคารและช่างก่อนเข้าคำนวณ เช่น `"เครื่องปรับอากาศ" -> "แอร์"`, `"โคมไฟ" -> "หลอดไฟ"`, `"สุขภัณฑ์" -> "ชักโครก"`
3. **ยึดมั่นใน Human-in-the-loop:**
   - ผลการทดสอบยืนยันชัดเจนว่า **การให้มนุษย์ (Staff) ตัดสินใจในขั้นตอนสุดท้าย สามารถดักจับ False Positive ได้ 100%**
4. **ติดตั้ง Debounce Queue:**
   - ช่วยลดปริมาณข้อความในกลุ่ม LINE ได้ถึง 90% ช่วยแก้ปัญหาแชทแตกได้อย่างเด็ดขาด

## 9. ตารางสรุปผลเปรียบเทียบแยก 2 ปัญหา (Final Summary Matrix)

| ปัญหาหลัก (Problem) | เทคนิคที่ใช้ (Technique) | รูปแบบการทดสอบ (Test) | ผลการทดสอบ (Result) | สถานะ (Status) | ขั้นตอนถัดไป (Next Step) |
|---|---|---|---|:---:|---|
| **Duplicate Request** | Rule-based Scoring | ทดสอบ 15 Similar + 6 Distinct | ตรวจจับเคสซ้ำได้ 100%, พบ False Positive 2 เคส | **PASS** | ปรับ Gate Location ขั้นต่ำ |
| **Duplicate Request** | `pg_trgm` Matching | ทดสอบ 7 คู่คำ | ตัวสะกดคล้ายทำได้ดี, คำพ้องความหมายได้คะแนนต่ำ | **PASS WITH NOTES** | เพิ่ม Synonym Normalization |
| **Duplicate Request** | Human-in-the-loop | จำลอง Accept / Reject 3 Scenarios | Staff ดักจับเคสต่างห้องได้ 100% และบันทึกเหตุผลครบ | **PASS** | นำไปสร้าง UI แท็บ Suggestion |
| **Duplicate Request** | Bulk Action & Logs | สั่งเปลี่ยนสถานะ 15 รายการพร้อมกัน | สำเร็จ 15 รายการ, สร้าง Log เชื่อม `bulk_action_id` ครบ | **PASS** | นำไปเชื่อมต่อกับ API |
| **Request Surge** | Surge Detection | ทดสอบ 3 ระดับ (Normal, Surge, High) | ตรวจจับและปรับโหมดตามความถี่ได้ถูกต้อง | **PASS** | กำหนด Threshold ใน Config |
| **Request Surge** | Notification Queue | จำลอง State Machine 100 รายการ | จัดลำดับคิวและเปลี่ยนสถานะถูกต้อง | **PASS** | นำไปสร้างตารางใน Database |
| **Request Surge** | Debounce & Aggregate | จำลอง 20 คำร้องใน 5 นาที | ลดข้อความจาก 20 เหลือ 2 ข้อความ (ลดลง 90%) | **PASS** | พัฒนา Worker Background Job |
| **Request Surge** | Exponential Retry | จำลอง Timeout + Rate Limit | Retry 3 ครั้งและคำนวณ Backoff ถูกต้อง | **PASS** | ใส่ใน Handler ของ Worker |
| **Request Surge** | Idempotency Key | ยิง Event เดิมซ้ำ 2 ครั้ง | ดักจับข้อความซ้ำได้ 100% | **PASS** | ใช้งานในทุก Push Event |
| **Request Surge** | Advisory Lock | ตรวจสอบ Lock ใน Database จริง | ยังไม่มีฟังก์ชัน Lock ใน Production DB | **NOT IMPLEMENTED** | สร้างใน Migration Phase 2 |
| **Request Surge** | LINE Group Delivery | ยิงข้อความจริงเข้ากลุ่ม `SOC TEST` | ได้รับ HTTP 200 OK ข้อความเข้ากลุ่มทดสอบสำเร็จ | **PASS** | ยึด Dynamic Query เป็นมาตรฐาน |
